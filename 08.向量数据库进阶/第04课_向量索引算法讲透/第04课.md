# 第 04 课　向量索引算法讲透

第 7 章第 02 课，我们在 FAISS 里第一次见到 IVF、HNSW、PQ，还亲手拧过 nprobe、efSearch 这些旋钮。本课不重复拧旋钮，而是换个视角：**离开 FAISS 你会发现，这三种思路根本不属于任何一家**——它们是整个向量检索圈的通用操作系统。Chroma、Milvus、PGVector 菜单上的索引类型，全是这三招的排列组合。

## 三招省法，复习成一句话

- **IVF：省计算**。先分堆，查询只搜最近的几堆（图书馆按主题分楼层，直奔烹饪区）。
- **HNSW：省路径**。图上先粗后细，几大步跳到目标附近（查字典先翻 Z 区，再找 zhang）。
- **PQ：省存储**。有损压缩，向量只记"每段的代表编号"（JPEG 压图，肉眼看着差不多就行）。

真实系统经常组合出拳：IVF+PQ = 先分堆缩小范围，堆里再压缩着算——海量数据的黄金搭档。

## PQ 手算：压缩率这笔账，今天亲手算

PQ 听着玄，账很好算。一个 128 维向量，每个数 4 字节，占 512 字节。切成 16 段，每段用 256 个"代表向量"之一来顶替——每段只需记 1 个字节编号，总共 16 字节，**压缩 32 倍**。代价：存的是"代表"不是原身，距离只能"估"，会有一点误差。

```mermaid
flowchart LR
    V[8维原向量] -- 切成2段x4维 --> S1[前半段]
    V --> S2[后半段]
    S1 -- 离哪个代表最近 --> C1[编号 0]
    S2 -- 离哪个代表最近 --> C2[编号 1]
    C1 --> CODE[编码 0,1 共2字节]
    C2 --> CODE
    CODE -- 解压=代表的拼接 --> R[重建向量 约等于原向量]
```

别小看这个 2 字节的小例子——真实 PQ 的流程一模一样，只是段落更多、代表库更大（256 个代表恰好 1 个字节编号）。

## 各库菜单对比：同一原理，不同上菜方式

| 库 | 索引菜单 | 谁来选 |
|----|---------|--------|
| FAISS | Flat / IVF / HNSW / PQ 全家桶 | 你自己选（第 7 章练过） |
| Chroma | 默认 HNSW 系 | 它替你选 |
| Milvus | IVF_FLAT / IVF_SQ8 / IVF_PQ / HNSW 等，菜单最全 | 你选，可按数据换 |
| pgvector | ivfflat、hnsw 两种 | 你选，二选一 |

看出来了吗：**算法是公用的，差别只在"给不给你选、替不替你调"**。Chroma 省心但没得挑；Milvus 自由但你要懂行——这份"自由与负担"的权衡，正是下一课选型的核心议题。另一个提醒：建索引时还要指定"距离度量"（L2 / 内积 / 余弦），它和索引算法是两个独立旋钮，别拧混了。

## 想一想

1. 压缩 32 倍的 PQ，什么场景"误差换内存"血赚？什么场景完全不能接受？
2. Chroma 不让你选索引，Milvus 给你一整面墙的选项。作为使用者，你更愿意为什么买单？
3. IVF+PQ 组合拳里，两招分别省的是什么？只有 10 万条数据时值得上这套组合吗？
4. 轻动手：把 index_algorithms.py 的码本从每段 2 个代表改成 4 个，重建误差和编码体积各怎么变？

## 小结

- IVF 省计算、HNSW 省路径、PQ 省存储：三招通用，不属于任何一家库。
- PQ 切段编码，压缩率 = 原字节数 ÷ 编码字节数，代价是估计误差。
- 各库差异不在算法，而在菜单自由度与默认策略。
- 索引算法 × 距离度量是两个独立旋钮，分开拧。
