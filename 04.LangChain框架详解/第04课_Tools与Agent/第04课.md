# 第 04 课　Tools 与 Agent

上一课你把 Function Calling 的闭环走了一遍：发工具说明、执行、回填，模型已经会"用工具"。但那套代码写起来相当繁琐：工具说明要手工拼 JSON，模型回复要自己解析，执行结果要自己回填，模型连续调用多轮还得自己写循环。

这一课先看 LangChain 怎么把这些重复劳动接管，再讨论一个更进一步的问题：模型会用单个工具了，能不能给它一组工具和一个目标，让它自己决定先做哪件、后做哪件？这就是 Agent。

---

## 一、框架替你省了什么

回忆第 3 课的闭环，里面全是重复劳动：

- 把函数名、参数说明拼成一份 JSON 工具清单，随请求发给模型；
- 从模型回复里认出它想调用哪个函数、参数是什么；
- 执行函数，把结果转成文本回填进对话；
- 模型如果继续发起调用，回到第一步再来一轮。

LangChain 把这些封装成两个组件：`Tool` 负责把你的函数翻译成模型能读懂的工具说明，`Agent` 负责把"调用、执行、回填"的循环自动跑起来。你只写函数本身，翻译和循环都归它管。

> 老规矩，先看"不用框架要写多少"。上一课的 function_calling.py 已经替你答了：光闭环就五六十行样板。框架没有引入新能力，它只是把这些提前写好了。

## 二、定义工具：@tool 最省事

最常用的方式是 `@tool` 装饰器：普通函数加一行，就变成模型能用的工具。

```python
from langchain_core.tools import tool

@tool
def get_weather(city: str) -> str:
    """查询北京/上海/广州当天的模拟天气。其他城市不要调用，直接告知用户暂不支持。"""
    data = {"北京": "晴，最高 18℃", "上海": "多云，最高 22℃", "广州": "阵雨，27℃"}
    return data.get(city, f"暂无 {city} 的数据")
```

它自动完成三件事，全部从函数身上读取：

- docstring 变成工具说明：就是给模型看的那段 description，告诉它这个工具做什么、什么时候该用；
- 参数类型标注变成参数 schema：`city: str` 会被翻译成"需要一个字符串参数 city"；
- 函数体变成执行逻辑，由你的程序在本地真正运行。

所以 docstring 不是写给人的注释，而是写给模型的说明。写得含糊，模型就会在不该调用的场景调用它：你只支持三个城市，docstring 只写"查天气的"，用户问"成都天气"它照样调用，结果只能返回"暂无数据"。参数描述同理，"中文城市名，如：北京"比只写 `city: str` 返工率低得多。

装好后的工具用 `.invoke()` 直接调用，传参用字典：

```python
print(get_weather.invoke({"city": "北京"}))
print(get_weather.args)   # 看看模型看到的参数说明书长什么样
```

## 三、需要更多控制时：Tool 与 BaseTool

`@tool` 覆盖大多数场景。需要更细的控制时，还有两条路。

`Tool` 类适合"函数已经写好，直接包装"的情况：

```python
from langchain_core.tools import Tool

calc = Tool(
    name="calculator",
    func=lambda e: str(eval(e)),      # 仅示意，eval 有注入风险，真实代码见本课 demo
    description="计算一个算术表达式",
)
```

`BaseTool` 基类适合复杂工具：参数校验想用 Pydantic 模型、逻辑想写成类、状态想在多次调用间复用：

```python
from langchain_core.tools import BaseTool
from pydantic import BaseModel, Field

class WeatherInput(BaseModel):
    city: str = Field(description="中文城市名，如：北京")

class WeatherTool(BaseTool):
    name: str = "get_weather"
    description: str = "查询北京/上海/广州的模拟天气，其他城市不要调用"
    args_schema: type = WeatherInput

    def _run(self, city: str) -> str:
        return {"北京": "晴 18℃"}.get(city, "暂无数据")
```

顺带说异步：如果工具本身就是网络请求，把函数写成 `async def`，调用改用 `await tool.ainvoke({...})`，其余不变。入门阶段用同步的完全够。

## 四、内置工具，以及出错怎么办

LangChain 社区维护了一批现成工具，不用每个都自己写：

| 工具 | 干什么 | 注意 |
|------|--------|------|
| Wikipedia 查询 | 查百科条目 | 需装 langchain-community |
| Tavily / SerpAPI 搜索 | 搜索引擎 | 需要各自的 API Key |
| Python REPL | 跑 Python 代码 | 高危：等于给模型 shell |
| Shell 工具 | 执行系统命令 | 同上，慎给 |

接入方式都是"包装类套一层 API 包装器"两行代码，用到哪个查哪个的文档即可。真正的重点在于：**工具会出错**。搜索额度用尽、订单号不存在、表达式残缺，这些情况你在第 3 课处理过：错误信息要当作执行结果回填给模型，模型会自己调整说法，程序不能当场中断。

LangChain 把这个机制做成了开关：工具内部抛 `ToolException`，并告诉框架把错误转成回复文本：

```python
from langchain_core.tools import StructuredTool, ToolException

def query_order(order_id: str) -> str:
    """按订单号查询订单状态，order_id 形如 SO-2026-0001。"""
    raise ToolException(f"订单 {order_id} 不存在，请确认订单号后重试")

query_order_tool = StructuredTool.from_function(
    func=query_order,
    name="query_order",
    handle_tool_error=True,  # 开关打开：ToolException 转成回复文本，程序不崩
)
```

这样 `query_order_tool.invoke(...)` 拿到的就是那句"订单不存在"，模型看到后会换一种方式回应用户。注意版本差异：v1.x 的 `@tool` 装饰器工厂已经不接收 `handle_tool_error` 参数（老代码里 `@tool(handle_tool_error=True)` 现在会直接报 TypeError），开关要开在工具对象上。更简单的做法是在函数里 try/except，直接返回一句友好的中文说明，效果类似。原则不变：错误是数据，不是事故。

## 五、Agent：路径由模型临场决定

到这里，"用工具"和"用 Agent"的区别可以讲清楚了：

- **固定链**像景区的观光大巴：先停 A 站再停 B 站，路线在你写代码时就定死了；
- **Agent** 像一个拿着工具箱的助理：你只交代目标，"查查北京和上海今天哪个热，温差多少"，它自己决定先查哪座城市、要不要用计算器；换个任务，步骤又是另一套。

关键差异一句话：**链的路径是你预先写死的，Agent 的路径是模型临场决定的**。所以 Agent 的运行核心是一个循环：想一步、做一步、看结果、再想下一步：

```mermaid
flowchart TD
    S[用户交给 Agent 一个任务] --> T{模型思考：现在该干嘛？}
    T -->|自己就能答| D[直接写出最终回答]
    T -->|需要用工具| P[选定工具并填好参数]
    P --> X[框架执行工具，拿到结果]
    X --> F[结果回填进对话记录]
    F --> T
    D --> E[任务完成]
```

这个"思考 → 选工具 → 执行 → 回填 → 再思考"的循环，正是第 3 课你手写的那段 while 循环。Agent 只是把这个循环里的判断也交给了模型：它认为信息够了，就不再发起调用，直接作答结束。

## 六、v1.x 怎么搭一个 Agent

旧版教材里大量出现的 `AgentExecutor`、`create_openai_functions_agent`、`initialize_agent`，在 LangChain v1.x 里都已淘汰。现在统一用一个入口：

```python
import os
from langchain.agents import create_agent
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(
    model="gpt-4o-mini",  # 示例名，可能已更新：按官网模型列表选当前便宜够用的
    api_key=os.environ.get("OPENAI_API_KEY"),
)

agent = create_agent(
    model=llm,
    tools=[get_weather, calculator],
    system_prompt="你是助理。只能用提供的工具查天气和做计算，答不了的直说，不要编。",
)

result = agent.invoke({"messages": [{"role": "user", "content": "北京和上海今天哪个更热？温差多少？"}]})
print(result["messages"][-1].content)
```

三样东西传进去：模型、工具列表、系统提示。返回的 `result["messages"]` 是完整对话记录，最后一条就是答案；前面几条里能看到它调用了哪个工具、参数是什么，调试时很有用。

再说 **Middleware（中间件）**，它是 v1.x 的新机制：在模型每轮决策前后统一插入逻辑。第 3 课讲记忆时讨论过"历史太长怎么办"，在这里一个现成的中间件就能挂上：

```python
from langchain.agents.middleware import SummarizationMiddleware

agent = create_agent(
    model=llm,
    tools=[get_weather, calculator],
    system_prompt="你是助理。",
    middleware=[
        SummarizationMiddleware(model=llm),  # 对话太长自动摘要，呼应第 03 课的记忆问题
    ],
)
```

护栏、结构化输出（呼应第 01 课的 Runnable 与第 03 课的 Memory）也都有对应中间件，思路一致：把能力做成可插拔的组件，按需挂载。中间件的具体参数随版本演进较快，使用时以官方文档为准。

> 老教程对照，会读即可：`AgentExecutor + create_openai_functions_agent`、`initialize_agent`、`AgentType` 枚举，全部被 `create_agent` 取代；新代码不要再使用那些写法。`create_agent` 内部基于 LangGraph 跑循环，循环步数等管理也不再需要手动配 `max_iterations`。

## 七、让 Agent 靠谱的五道保险

Agent 的路径不受你控制，也就可能跑偏。几道保险按成本从低到高排：

1. 说明书写清楚：docstring 里写明用途、边界、参数格式，这是成本最低、收益最大的一道；
2. 系统提示划边界："只允许做这几件事，做不到就直说"，减少它超出范围的发挥；
3. 危险工具留确认：删数据、发邮件、付款这类动作，用人工确认中间件先交给人核实再执行；
4. 循环步数封顶：限定最多几轮，防止它在同一类调用上无限循环、持续消耗费用；
5. 出错友好回填：工具错误友好地回填，它多半会换一种方式重试，而不是一路错到底。

最后一个判断最重要：简单固定的流程，别用 Agent。三步以内、路径确定的任务，一条 LCEL 链更快、更稳、更省钱；Agent 每一步都要模型参与决策，更贵、更慢，结果还带随机性。它适合"路径无法预知"的任务。

## 小结

LangChain 用 `@tool` 把"函数 + docstring + 类型标注"自动翻译成模型能读懂的工具说明，把第 3 课手写的解析、执行、回填样板全部接管；参数复杂时再用 Tool 类或 BaseTool 基类。工具会出错，错误要当数据回填给模型，而不是让程序中断。Agent 则更进一步：给模型一组工具和一个目标，让它自己"思考→选工具→执行→回填→再思考"，路径临场决定，这是它与固定链的本质区别。v1.x 用 `create_agent` 一个入口搭 Agent，Middleware 把记忆、护栏、结构化输出做成可插拔组件，旧的 AgentExecutor 写法已淘汰。最后记住：说明书、边界、确认、步数上限、错误回填是 Agent 的五道保险；路径固定的简单流程，用链，不用 Agent。
