# 第 07 课　综合实战：组装一个能跑的小应用

组件到这一课已经凑齐：第 01 课认了 LangChain 的骨架，第 02 课会用竖线串链，第 03 课让模型记得前文，第 04 课给它配了工具，第 05 课接上检索，第 06 课让输出变成规整的对象。这一课把它们装起来，做一个能跑的小应用：**基于几条小资料回答问题、带多轮记忆、必要时还会调用工具**。

这一课还有一个目标：讨论清楚"到底值不值得用框架"。第五节专门回答这个问题，别跳。

## 一、先看全景：一条数据流

写代码之前先把数据流想清楚：

```mermaid
flowchart LR
    Q[你的问题] --> R[检索器<br/>从资料里捞最相关的几条]
    R -- "最相关的 k 条资料" --> P[提示模板<br/>资料 + 问题 + 历史占位]
    H[记忆<br/>checkpointer + thread_id] -- "前几轮聊过什么" --> P
    P --> M[模型<br/>决定：直接答还是用工具]
    M -- "不会算数/不知道时间" --> T[工具<br/>@tool 白名单计算器 · 报时]
    T -- "结果回填" --> M
    M --> O[输出解析器<br/>抽出纯文本回答]
    O --> A[回答]
```

对照图看职责：检索负责从资料里找出最相关的几条；记忆负责把前几轮对话带进提示；模型负责决定直接回答还是调用工具；工具补充模型不擅长的精确计算、报时；输出解析把回答整理成程序能直接用的文本。每一课学的组件，在这条流程上都有明确的位置。

## 二、项目结构与配置

配套代码只有一个文件 `mini_app.py`，按"能不能离线跑"切成三段：

```
第07课_综合实战/
└── mini_app.py
    ├── 第①段 offline_demo()     纯标准库：资料 + 假向量检索 + 拼提示（离线真跑）
    ├── 第②段 langchain_demo()   LangChain 外壳：检索器 + 提示模板 + 工具（离线可跑）
    └── 第③段 online_demo()      通电：LCEL 链 + Agent + 记忆（需 API Key）
```

三条配置纪律，前几课立过规矩，这里一次收齐：

- **Key 只从环境变量读**：`os.environ.get("OPENAI_API_KEY")`，代码里永远不出现真实 Key；可以用 python-dotenv 从同目录 `.env` 读，但 `.env` 不提交到仓库。
- 模型名不写死过时型号：代码里给的只是示例名，实际按官网模型列表选当前便宜够用的那一个。
- 资料固定写在代码里：本课就 5 条中文小资料，直接写在列表里，不依赖任何外部文件——目标是把流程跑通，而不是搭生产系统。

资料要固定的原因：初学阶段每多一个外部依赖（文档目录、向量库服务、网络），"跑不起来"的概率就上升。先把流程本身看明白，第 5 章再把真文档、真向量库换进来。

## 三、逐段组装

### 第①段：手动挡把原理跑一遍（离线真跑）

框架好用，但第一遍你要知道它在替你做什么。所以第①段不用任何框架，把"向量检索 + 拼提示"两个核心动作手动实现一遍：

```python
DOCS = ["LangChain 把大模型应用的零件都做好了……", "LCEL 用竖线把零件串成链……", ...]

def hand_embed(text):            # 假的"嵌入"：数锚点词出现几次，凑成一个向量
    return [text.count(a) for a in ANCHORS]

def cosine(a, b):                # 两个向量的余弦相似度：方向越一致，意思越近
    ...

def retrieve(question, k=2):     # 检索三步：算相似度 → 排序 → 取前 k 条
    ...
```

`hand_embed` 是个简化办法：数几个锚点词的出现次数当向量。真的嵌入模型是神经网络，效果远好于数词，但"把文本变成一串数字，再比较相似度"这件事的流程形状，两者完全一致。简化实现的效果差，胜在离线可跑、每一步都看得见。

跑起来你会看到检索结果和拼好的提示文本：

```
问题：LCEL 怎么把零件串起来？
检索结果（假向量 + 余弦相似度）：
  相似度 0.707  LCEL 用竖线把零件串成链……
  相似度 0.577  LangChain 把大模型应用里反复出现的零件都做好了……

拼好的提示长这样：
----------------------------------------------
仅根据以下资料回答问题，资料里没有就直说不知道。

资料：
- LCEL 用竖线把零件串成链……
- LangChain 把大模型应用里反复出现的零件都做好了……

问题：LCEL 怎么把零件串起来？
----------------------------------------------
```

这两块输出，就是后面所有 RAG 链的本质：检索找出资料，模板把资料和问题装进同一个提示。第②段开始，让框架接管这些手工活。

### 第②段：换上 LangChain 的外壳（离线可跑）

第①段的函数要接进框架，得实现它的接口。`Embeddings` 是 LangChain 定的嵌入接口（`embed_documents` / `embed_query` 两个方法），写一个 `HandEmbeddings` 把简化向量实现包装进去，就能在框架里替代真嵌入模型：

```python
class HandEmbeddings(Embeddings):
    def embed_documents(self, texts):
        return [hand_embed(t) for t in texts]
    def embed_query(self, text):
        return hand_embed(text)

store = InMemoryVectorStore(HandEmbeddings())       # 内存向量库，零配置
store.add_documents([Document(page_content=t) for t in DOCS])
retriever = store.as_retriever(search_kwargs={"k": 2})  # 一行拿到标准检索器
```

这是第 05 课"格式统一"的收益：接口对上，`HandEmbeddings` 和 `OpenAIEmbeddings` 可以随时互换，链的其余部分一行不改。

接着拼提示模板，给记忆留位置：

```python
prompt = ChatPromptTemplate.from_messages([
    ("system", "你是资料问答助手，仅根据资料回答，资料里没有就直说不知道。"),
    MessagesPlaceholder("history", optional=True),   # 多轮历史在这里占座
    ("human", "资料：\n{context}\n\n问题：{question}"),
])
```

再把第 04 课的工具挂上。工具逻辑是纯标准库：一个只放行数字和四则运算的白名单计算器（用 `ast` 解析后逐节点检查，绝不直接 `eval` 模型给的字符串），一个报时函数：

```python
@tool
def calc_tool(expression: str) -> str:
    """计算一个只含数字与 + - * / 的算式。需要精确计算时调用。"""
    return safe_calc(expression)
```

`@tool` 干的活没变：把"函数 + docstring + 类型标注"翻译成模型能读懂的说明。工具逻辑始终是你自己的 Python，框架只负责传递：把说明递给模型，把模型的决定递回来。

### 第③段：通电（需 API Key，未实跑）

组件就位，接上模型。跑法一是固定链：检索 + LCEL + 输出解析，路径固定，问题进去、回答出来：

```python
rag_chain = (
    {"context": retriever | format_docs,   # 这一灶：问题 → 资料
     "question": RunnablePassthrough()}    # 这一灶：问题原样通过
    | prompt
    | model
    | StrOutputParser()
)
rag_chain.invoke("LCEL 怎么把零件串起来？")
```

说明一处口径：这里代码块里的 `prompt` 沿用第②段带 history 占位的模板；`mini_app.py` 第③段实际运行时用的是不带 history 的简化模板（固定链演示单轮问答够用），要多轮记忆时换成第②段的模板并填 history 即可。Agent 路线的多轮记忆由 checkpointer 负责，不依赖这个占位。

跑法二是 Agent：路径不固定，模型自己决定调不调工具，问"帮我算 12 * 3 + 4"它会去调计算器。记忆也在这段接上：`create_agent` 配一个 `InMemorySaver` 存档器，同一段对话共用一个 `thread_id`，历史自动带回：

```python
agent = create_agent(
    model=model,
    tools=[now_time_tool, calc_tool],
    system_prompt="你是资料问答助手，回答简短。",
    checkpointer=InMemorySaver(),   # 存内存：程序重启就没了；跨重启换 SQLite 等实现
)
config = {"configurable": {"thread_id": "chat-1"}}
agent.invoke({"messages": [...]}, config)   # 同一个 config 连问，它记得前文
```

注意分工：固定链管"每次都一样"的流程，Agent 管"临场决定"的流程。这个应用两条路都用：资料问答路径固定，所以走链；要不要用工具临场才定，所以走 Agent。

## 四、运行与排错

```bash
python mini_app.py
```

没装 LangChain：只有第①段输出，照样能看懂原理。装了没配 Key：第①②段完整输出，第③段打一行中文提示后跳过，不会抛 traceback。配好 Key：三段全跑，第③段会产生少量费用。

跑不通时，最重要的方法是把链拆开逐段验证。链像一串彩灯：整串不亮，你不会整串扔掉，而是一颗一颗拧下来试。LCEL 的每个组件都是独立 Runnable，拆开来 `.invoke()` 一次就能定位问题：

```python
docs = retriever.invoke(question)        # 先单测检索：捞上来的资料对不对？
print(docs)                              # 捞错了 → 查 embedding 和 k
step2 = {"context": format_docs(docs), "question": question}
print(prompt.invoke(step2).messages)     # 再单测模板：坑位填对了吗？资料塞进去了吗？
```

定位方法一句话：打印每个组件的输入和输出。检索空了查资料入库；提示里资料是空的查 `format_docs`；回答跑题查 system 提示。每一截的进出口都看得见，错误藏不住。

## 五、框架的边界：什么时候用，什么时候别用

讲到这里，必须回答一个更根本的问题：这个应用不用 LangChain 行不行？

答案是行。第①段你已经看到了：检索加拼提示，二十行标准库就够了。如果应用只有"一次调用、一个提示"，直接用第 3 章的裸 SDK 反而更直接。那框架什么时候真省事？

这些时候它确实帮你省事：

- 组件多：检索 + 记忆 + 工具 + 解析串在一起时，LCEL 的管道和字典汇合确实省掉大量胶水代码；
- 要横切能力：流式输出、异步并发、失败重试、结构化解析，这些"每个应用都要、每个都难写"的部分，框架全有现成实现（第 02 课 `.with_retry()` 一行的事）；
- 要换模型：今天用 A 家明天换 B 家，统一接口换一个类名就行；
- 集成多：几十种向量库、文档加载器，自己逐个接成本高。

这些时候它让你负担变重：

- 抽象层叠抽象层：链一长，报错从框架深处冒出来，堆栈穿过多层包装，初学者难以定位——本章你亲手拆链调试，就是为这种时刻准备的；
- 版本更新耦合：LangChain 演进快，老教程的写法可能已经淘汰（本章提到的旧 Memory 类、AgentExecutor 就是例子），升级要跟着迁移；
- 简单任务被复杂化：就发一次请求、收一段文本，套上框架反而多绕一层。

给你一个动手前的判断清单，按顺序核对：

1. 组件数量：一次调用能解决 → 裸 SDK，别上框架；
2. 换模型与集成：会频繁换模型，或有现成集成可直接用 → 框架的统一接口开始有价值；
3. 横切能力：需要流式/异步/重试/结构化输出 → 框架的横切能力有价值；
4. 成本核算：愿意为省样板代码支付调试和版本迁移的成本 → 上；不愿意 → 用裸 SDK 把核心流程写清楚。

记住本课的第①段：你手动写过一遍的东西，才是你能放心交给框架的东西。框架省的是重复劳动，省不掉理解——理解不在了，框架就只剩麻烦。

## 想一想

1. 第①段的假向量只数锚点词。如果两个问题的意思相近但用词完全不同（"怎么省钱" vs "如何控制成本"），这套检索会发生什么？真嵌入模型为什么能解决？
2. `create_agent` 配上 `checkpointer` 之后，为什么换一个 `thread_id` 就像开始了一段全新对话？如果要把聊天记录存到数据库让用户第二天接着聊，该换哪个组件？
3. 判断清单第 4 问里"调试和版本迁移的成本"，结合你跑本课代码的体验，具体指什么？如果一个团队只有"一次调用加一个提示"的需求，你会推荐他们用什么？
4. 动手（选做）：往 `DOCS` 里加一条新资料，跑第①②段对比检索结果；再把 `mini_app.py` 第③段的 `thread_id` 换个新值，观察第 2 轮还记不记得第 1 轮说过的话。

## 小结

组装应用的顺序永远是先画数据流再写代码：资料 → 检索 → 提示（带记忆占位）→ 模型（可调工具）→ 解析输出。离线段用假向量把"嵌入 → 相似度 → 取前 k 条 → 拼提示"跑通，你就懂了 RAG 的骨架；框架段把这些手动活换成标准组件，`Embeddings` 接口一对上，简化向量实现和真嵌入模型可以互换。固定链管路径确定的流程，Agent 管临场决定的流程，`checkpointer + thread_id` 管多轮记忆。链出问题就拆开逐组件 `.invoke()`，打印每个进出口。最后记住框架的边界：组件多、要横切能力、常换模型，它省事；一次调用的小任务，裸 SDK 更直接。先手动理解，再放心托付。
